Батч в ComfyUI — списки вместо циклов, почему превью появляются только в конце, почему писатель не может быть списковым и где seed'ы молча совпадают

**Граница записи:** ниже сохранены исходные наблюдения и причины решений. Замеры, версии окружения и слова «сейчас» относятся к дате соответствующего наблюдения; это не повторная проверка на новом окружении. Порядок чтения и ограничения: [инженерная память](README.md#как-читать-записи).

# Батч-менеджер: что прочитано в ядре 29.08.2026

Задача звучала так: «сто картинок → сто промптов, и чтобы они писались по ходу,
а не в конце» плюс «сто уникальных промптов, каждый новой итерацией, чтобы
контекст не деградировал». Ответы нашлись в ядре, а не в паках сообщества.

## Цикл не нужен: батч-движок уже есть

`execution.py`, `_async_map_node_over_list`:

```python
for i in range(max_len_input):
    input_dict = slice_dict(input_data_all, i)
    await process_inputs(input_dict, i)
```

Списковый вход заставляет ядро вызвать `execute` по разу на элемент, и это
распространяется вниз по всей ветке. Значит:

- «Свежая итерация» получается сама: каждый вызов независим, и модель заводит
  новый разговор — контексту накапливаться негде.
- `slice_dict` повторяет ПОСЛЕДНИЙ элемент более короткого входа, поэтому
  скалярный выход (у нас `total`) сам размножается на все итерации.

В ядре есть и `CreateList` (`comfy_extras/nodes_toolkit.py`, алиасы «Iterator»),
и настоящие циклы через node expansion (`enable_expand` + `NodeOutput(expand=…)`).
Циклы нужны, когда результат N влияет на N+1; для независимых заданий список
проще и не рассыпается при ошибке в середине.

Паки сообщества с for-циклами (Easy-Use, 0246, ControlFlowUtils,
comfyui-job-iterator) на машине НЕ стоят и не понадобились.

## ⚠️⚠️ Список идёт ВШИРЬ: нода целиком, потом следующая

Самый дорогой факт всей темы, и он получен ЗАМЕРОМ на живом сервере, а не из
чтения кода. Три задания, цепочка источник → загрузчик → писатель:

```
[TS Batch Load Image] probe_1.png
[TS Batch Load Image] probe_2.png
[TS Batch Load Image] probe_3.png
[TS Batch Write] 1/3
[TS Batch Write] 2/3
[TS Batch Write] 3/3
```

`_async_map_node_over_list` — цикл ВНУТРИ одной ноды, поэтому ядро доводит до
конца все её копии и лишь затем берётся за следующую. Отсюда два следствия,
каждое ломает свой сценарий и оба невидимы, пока не проверишь:

1. **Инкрементальная запись со списком не работает.** Писатель стартует, когда
   модель уже сделала ВСЁ. Файл заполняется в конце — ровно то, чего просили
   избежать.
2. **`TS_ImagePromptInjector` при списке портит метаданные.** Он правит общий
   `hidden.prompt`; сто вызовов подряд оставляют последний промпт, а `SaveImage`
   отрабатывает после — и все сто картинок подписаны одинаково.

**Лечение — `one_per_run` у `TS_BatchSource`**: одно задание за прогон очереди,
Batch count = число заданий. Каждый прогон — полный проход по графу, поэтому
картинка сохранена и подписана до начала следующей. Курсор живёт в module-level
`_Cursor` (класс V3-ноды заблокирован), ключ — сама задача, так что два
источника в графе не сбивают счёт друг другу.

⚠️ Отпечаток в этом режиме обязан быть уникальным, иначе прогон возьмут из кэша
и курсор не сдвинется. **`time.time_ns()` для этого НЕ годится**: на Windows он
квантован примерно 15 мс, два вызова подряд дают одно число (проверено упавшим
тестом). Рядом положен счётчик тиков, который ничьей не даёт.

Живая проверка всей цепочки с настоящей моделью: две картинки → две разные
верные подписи, по строке на каждую, файл дописывался между прогонами.

## ⚠️ Превью в интерфейсе НЕ появляются по ходу

`get_output_from_returns` копит `ui` со всех N вызовов в список, и
`server.send_sync("executed", …)` уходит ОДИН раз, после последней итерации
(`execution.py:563-578`). Сто картинок появляются в холсте разом, в конце.

При этом на ДИСКЕ они оказываются сразу: `SaveImage` вызывается каждую итерацию
и пишет файл немедленно. То есть «видеть по мере генерации» через папку
работало и до нас.

Обход для интерфейса — прогресс, а не UI-выход: `set_progress` принимает
`preview_image` (`comfy_api/latest/__init__.py:40`), под ним синхронный
`ProgressBar.update_absolute(value, total, preview)` из `comfy/utils.py`.
Формат превью — кортеж `("JPEG", PIL.Image, max_side)`; прогресс-обработчик шлёт
его как `PREVIEW_IMAGE_WITH_METADATA` и НЕ батчит.

## ⚠️ Писатель обязан быть НЕсписковым

Самое хрупкое место всей конструкции. Объяви `TS_BatchWrite`
`is_input_list=True` — и ядро позовёт его один раз, после последнего задания.
Он по-прежнему всё запишет, тесты на содержимое файла пройдут, а единственное
свойство, ради которого нода есть («результат 47 на диске, пока считается
48-й»), исчезнет молча. Сторожится отрицательным тестом
`test_the_writer_is_not_a_list_node`.

Правило индекса: `index == 0` обрезает файл, любой другой дописывает. Отсюда
работает возобновление: `start_at=50` в источнике даёт `index=50`, и файл
прошлого прогона не стирается. Поэтому же источник НЕ перенумеровывает задания
после `start_at`.

## ⚠️ Батч картинок ≠ список картинок

`TS Qwen 3 VL` делает `processed_images.extend(engine.tensor_to_pil_list(image))`.
Тензор `[100,H,W,C]` — это для неё ОДНО обращение к модели со ста картинками:
один общий ответ и переполненный контекст, ровно то, чего просили избежать.
Нужен список из ста отдельных `[1,H,W,C]`. Разница не видна на схеме.

И вторая причина, по которой источник раздаёт ПУТИ, а не картинки: сто кадров
4K в кэше выхода — это 100 × 4096×2160×3×4 ≈ 10 ГБ. `TS_BatchLoadImage` читает
их по одной, пик — один кадр.

## Seed: где он молча совпадал

- **`TS Qwen 3 VL`** — seed есть, с `control_after_generate=True`. НО виджет
  один на все сто вызовов: при списковом прогоне все итерации получают одно
  число. Ради этого у источника есть выход `seed` — по производному значению на
  задание (`random.Random(f"{base}:{i}").getrandbits(32)`, а не `base+i`).
- **`TS Super Prompt`** — маршрут `/enhance` seed принимал с самого начала, но
  `grep -rn "seed" js/llm/` не находил НИ ОДНОГО упоминания: фронтенд его не
  слал, значит всегда брался фиксированный `SUPER_PROMPT_SEED = 42`, и повторное
  нажатие возвращало тот же текст при живой кнопке.
- **`TS Super Prompt RT`** — seed не было вовсе, хотя
  `litert_lm.SamplerConfig(top_k, top_p, temperature, seed)` его принимает
  (проверено `inspect.signature` на установленной 0.16.1).

Исправлено 29.08.2026: обе кнопки генерируют seed на каждое нажатие
(`freshSeed()`, 32 бита — столько переживает JSON без потери точности), а
фиксированный seed оставлен запасным вариантом для запроса без поля.

## Формат записи выбран не наугад

`TS_BatchWrite` в режиме блоков пишет их через пустую строку — ровно то, что
разбирает уже имевшаяся `TS_BatchPromptLoader`. Режим «строка на задание»
читается обратно самим `TS_BatchSource` (`Lines in text file`), и этим круг
замыкается: файл подписей становится файлом заданий на генерацию без единой
конвертации. Оба прохода закрыты тестами.

⚠️ В построчном режиме текст СХЛОПЫВАЕТСЯ (`" ".join(body.split())`). Модель
отвечает абзацами когда захочет, и двухстрочный ответ в файле «строка на
задание» тихо превращается в два задания при обратном чтении.

## Режим «Text files in folder» (06.10.2026)

Просьба владельца: папка, где каждый промпт — отдельный файл. Пятый вариант
комбо дописан В КОНЕЦ (умолчание `Images in folder` не трогали). `.txt` / `.md`,
естественный порядок, весь текст файла — одно задание (переносы строк внутри
СОХРАНЯЮТСЯ, в отличие от `Lines in text file`), BOM снимается (`utf-8-sig`),
пустые и больше 1 МБ пропускаются с записью в лог. Отпечаток смотрит на
текстовые суффиксы — картинка в той же папке кэш не сбрасывает.

Рецепт «картинка за картинкой с промптом в метаданных»: `one_per_run = true`,
Batch count у кнопки Run = числу файлов; `item` → текст позитивного энкодера И
вход `prompt` у `TS_ImagePromptInjector` (между VAE Decode и Save Image);
`seed` → сид сэмплера. Проверено вживую: 4 прогона → файлы 1, 2, 10, снова 1.
⚠️ Курсор живёт в памяти процесса: после перезапуска ComfyUI начнёт с первого
файла — продолжать через `start_at`.
