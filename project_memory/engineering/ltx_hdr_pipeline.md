## 1. Две технологии — не путать

У LTX **два** HDR-пути. Это разные технологии, а не два оттенка одной, и
`hdr_mode` в ноде настроек выбирает между ними.

| | нативный 2.5 | HDR IC-LoRA |
|---|---|---|
| ключ режима | `preserve HDR from EXR (ACEScct)` | `expand HDR from SDR (LogC3 IC-LoRA)` |
| что делает | **сохраняет** диапазон, пришедший из EXR | **выращивает** диапазон из обычного SDR |
| рабочая кривая | ACEScct | ARRI LogC3, EI 800 |
| линейная при коде 1.0 | **222.86** | **55.08** |
| примарии на выходе | AP1 → Rec.709 | ⚠️ **НЕ меняются** |
| опорный кадр | EXR (или обычная картинка) | обычный SDR |
| нужна LoRA | нет | да, IC-LoRA |
| статус | работает на 2.5 | проверена на 2.3; для 2.5 официально «в разработке» |

⚠️ **Отдать вывод одного пути обратной кривой другого — гарантированный сдвиг
цвета.** Режим едет с конфигом, и за ним следует всё: decode, потолок в
статистике, выбор ветки опорного кадра.

⚠️ **В пути IC-LoRA матрицу примариев применять НЕЛЬЗЯ.** Официальная нода
`LTXVHDRDecodePostprocess` раскодирует LogC3 и отдаёт линейный HDR как есть —
модель уже выдаёт нужные примарии.

Источники (проверены 17.08.2026): нативный путь требует EXR прямым текстом —
«Any EXR still or folder requires `--hdr`»; про LoRA — «validated on LTX-2.3; it
has not been validated on LTX-2.5 yet» и «LTX-2.5 support is in development».
Страницы: `docs.ltx.io/open-source-model/usage-guides/working-with-exr-hdr`,
`docs.ltx.io/open-source-model/advanced-workflows/hdr-video-beta`.

**HDR из SDR-кадра нативный путь не делает и делать не будет** — это другая
модельная технология. Что даёт JPG на входе, см. §4.

## 2. Что где лежит

`nodes/video/hdr/`, полка `TS/Video/HDR`, 2433 строки.

**Ядро — обычный Python с torch, БЕЗ ЕДИНОГО импорта ComfyUI.** Поэтому
тестируется без сервера и переносится куда угодно:

| файл | что в нём |
|---|---|
| `_acescct.py` | кривая ACEScct в обе стороны + обратная sRGB (для JPG) |
| `_logc3.py` | ARRI LogC3 в обе стороны |
| `_primaries.py` | Rec.709 ↔ AP1, матрицы ВЫВОДЯТСЯ из хроматичностей |
| `_resize.py` | ресайз в линейном свете, center_crop / reflect_pad |
| `_tonemap.py` | тон-маппинг ТОЛЬКО для превью |
| `_exr_io.py` | чтение и запись EXR, три бэкенда |
| `_hdr_types.py` | `HdrConfig`, `HdrImage`, режимы, статистика |

Прослойка и адаптеры (знают про `comfy_api`):

| файл | нода |
|---|---|
| `_schema.py` | имена пользовательских типов, `MISSING`, `CATEGORY` |
| `_vae.py` | загрузка VAE с явным dtype, один общий путь decode |
| `ts_ltx_hdr_settings.py` | `TS_LTXHDRSettings` — единственная галочка |
| `ts_ltx_hdr_load_exr.py` | `TS_LTXHDRLoadEXR` |
| `ts_ltx_hdr_guide.py` | `TS_LTXHDRGuide` — развилка и подготовка опорного кадра |
| `ts_ltx_final_latent_selector.py` | `TS_LTXFinalLatentSelector` |
| `ts_ltx_hdr_vae.py` | `TS_LTXHDRVAE` — тот же VAE в float32 |
| `ts_ltx_hdr_decode.py` | `TS_LTXHDRDecode` — единственный финальный декодер |
| `ts_ltx_hdr_stats.py` | `TS_LTXHDRStats` |

Направление зависимости между подпапками **одно**: `video/media` импортирует из
`video/hdr` (сохранятелю нужны запись EXR и тон-маппинг), обратно — никогда.

Публичные типы сокетов (менять нельзя, уезжают в workflow):
`TS_LTX_HDR_CONFIG`, `TS_LTX_HDR_IMAGE`.

### Сохранятель видео

`nodes/video/media/`: формат **«EXR sequence»** (float32 или 16-bit half, по
файлу на кадр в своей папке) и вход **`hdr_image`** — ПОСЛЕДНИМ в схеме.
Обычный вход `images` тоже принимается: чужой линейный HDR-тензор (например из
`LTXVHDRDecodePostprocess`) проходит без зажима — проверено значением 12.0.

EXR и превью пишутся **одним проходом** по кадрам: источником может быть поток
из файла, который второй раз не перемотать.

## 3. Отступления от плана (согласованы)

1. **Guide Pyramid + Guide Router слиты** в `TS_LTXHDRGuide`. Роутер требовал
   восьми проводов и отдельного типа ноды, притом что развилка и подготовка
   кадра — одна точка графа.
2. **Output Gate растворён в decode**: слот `hdr_linear` сам отдаёт
   `ExecutionBlocker` при выключенном HDR.
3. **EXR пишет TS Video Saver**, а не встроенная `Save Image (Advanced)` — по
   просьбе пользователя.
4. **Четвёртый бэкенд чтения — PyAV**, которого в плане не было.
5. **Вход `image_guide`** для обычной картинки — в плане не предусматривался.
6. **Режим LogC3** — план прямо запрещал смешивать пути; вместо смешивания
   сделан явный переключатель.

## 4. Числа, которые надо знать

- Потолок ACEScct: код 1.0 = линейная **222.86** (7.8 стопа над белым). Всё
  ярче сплющивается на входе в модель.
- Потолок LogC3: код 1.0 = линейная **55.08**.
- Белый SDR (линейная 1.0) = код ACEScct **0.5548**. То есть обычная картинка
  занимает нижние 55% диапазона, а сверху остаётся 45% — 7.8 стопа, куда модель
  МОЖЕТ уйти, но чего в JPG нет.
- Гамма JPG: код 0.5 = линейные **0.214**. Принять коды за линейный свет —
  ошибиться на **0.070** кода ACEScct на середине и до **0.131** в тенях; 0.131
  кода это **2.3 стопа**.
- Матрица Rec.709 → AP1 сходится с общепринятой до **4.8e-7**, строки дают
  ровно 1.0 (белый остаётся белым).
- Обратная LogC3 сходится с официальной формулой до **1.1e-8** на 2001 точке.
- Память: 129 кадров 1920×1088 float32 ≈ **3.01 ГиБ**, float16 ≈ 1.51 ГиБ.

## 5. ⚠️ Капканы цвета и EXR

**swscale молча зажимает float в `[0, 1]`.** Любая конверсия формата кадра в
PyAV идёт через него. Замерено: четырёхканальный EXR со значением 4.0,
прочитанный `to_ndarray(format="gbrpf32le")`, возвращается как **1.0**.

**PyAV не умеет `to_ndarray` для `gbrpf16le`** — «not yet supported». А
half-float это то, в чём рендерят почти все.

Оба закрыты разбором `frame.planes` руками. Порядок плоскостей у `gbrp*` —
**G, B, R** (замерено).

**OpenCV бесполезен как основной бэкенд.** `OPENCV_IO_ENABLE_OPENEXR=1` должна
стоять ДО импорта `cv2`, а его импортируют раньше нас и ядро
(`comfy_extras/nodes_sdpose.py`), и соседние кастом-ноды. Выставлять её в
`__init__.py` пака бессмысленно. Порядок «auto»: OpenImageIO → PyAV → OpenCV.

**У EXR-кодировщика ffmpeg нет сжатия.** Список опций пуст, `compression` он
отвергает. `format=half` работает и диапазон сохраняет (100.0 остаётся сотней).
Half+ZIP из плана потребовал бы OpenImageIO.

**Встроенная `Save Image (Advanced)` диапазон НЕ режет** — проверено побитово:
65000.0 и отрицательные значения доезжают до диска и обратно.

**Ветка LTX 2.4/2.5 VAE** (`decoder.conv_in_x_t.weight` в state dict) **не
переопределяет `process_output`** — работает штатное `(x+1)/2` с зажимом в
`[0, 1]`. Это НЕ потеря: рабочий сигнал там и живёт, HDR возвращается обратной
кривой уже после декодера. `working_dtypes` включает float32, так что
FP32-decode законен.

**Половинный опорный кадр готовится ИЗ ОРИГИНАЛА**, а не уменьшением полного:
официальный двухстадийный pipeline собирает image conditioning заново для
каждого разрешения, и усреднять надо линейный свет, а не логарифмические коды.

**`LTXVPreprocess` в HDR-ветке обходится полностью** — он гоняет кадр через
H.264 и восемь бит (`(image * 255.0).byte()` в исходнике ядра).
