LTX 2.5 VAE Decode «зависает» при полной VRAM — у декодера disable_offload=True и крупный резерв; лечит TS Free VRAM, не заплатка на ядро

Исходники темы: [ts_free_vram.py](../../nodes/utils/ts_free_vram.py).

**Граница записи:** ниже сохранены исходные наблюдения и причины решений. Замеры, версии окружения и слова «сейчас» относятся к дате соответствующего наблюдения; это не повторная проверка на новом окружении. Порядок чтения и ограничения: [инженерная память](README.md#как-читать-записи).

# LTX 2.5: декод VAE ползёт при забитой видеопамяти

Жалоба владельца 13.09.2026: после обновления ComfyUI генерация LTX 2.5 встаёт
на стадии VAE Decode — видеопамять под потолок, GPU 100%, скорость никакая.
LTX 2.3 на той же машине работал нормально; жалуются и другие.

## Разбор (по исходникам ComfyUI 0.35.1, НЕ замер)

Оба VAE попадают в **разные ветки** `comfy/sd.py`, и различаются не архитектурой,
а флагами подключения:

| | LTX 2.3 (`VideoVAE`) | LTX 2.5 (`CausalDiffusionVAE`) |
| --- | --- | --- |
| оценка памяти на декод | `1200 × T·H·W·512` | **`1700 ×`** — на 42% больше |
| `disable_offload` | не задан → `False` | **`True`** |
| класс патчера | `CoreModelPatcher` (динамика) | обычный `ModelPatcher`, `is_dynamic() → False` |
| загрузка | обычная | `force_full_load=True` — целиком, без выгрузки |

Выбор патчера делается тут же (`comfy/sd.py`):

```python
mp = comfy.model_patcher.CoreModelPatcher
if self.disable_offload:
    mp = comfy.model_patcher.ModelPatcher
```

История подтверждает, что старую ветку не трогали:

```text
ветка 2.3 (константа 1200):  50d6e1ca  2026-01-07  Tweak ltxv vae mem estimation
ветка 2.5 (константа 1700):  57ce8e1a  2026-08-11  Add support for LTX 2.5 (#15499)
```

То есть это не регрессия менеджера памяти, а конфигурация одной новой ветки VAE.

## ⚠️ Почему «зависает», а не падает

`VAE.decode` имеет запасной путь на тайловый декод, но он висит на `except`:
нужна ОШИБКА. На Windows при исчерпании VRAM драйвер NVIDIA не отдаёт OOM, а
выплёскивает память в системную. Исключения нет → тайлинг не включается →
декод идёт через PCIe и ползёт. В логе владельца строки
«Ran out of memory ... retrying with tiled» действительно НЕТ.

## ⚠️ Ложная улика: «0 models unloaded»

Эта строка НЕ означает, что ядро ничего не выгрузило.
`LoadedModel.model_unload` при удачной ЧАСТИЧНОЙ выгрузке возвращает `False`, а
`free_memory` считает только снятые целиком:

```python
if memory_to_free < self.model.loaded_size():
    freed = self.model.partially_unload(...)
    if freed >= memory_to_free:
        return False
```

Рядом есть и второе правило — динамические модели намеренно не выгружаются ради
других динамических (`if ... is_dynamic() and for_dynamic`). Для этого случая оно
не срабатывает (патчер VAE нединамический), но при чтении логов путает.

## Решение: нода, а НЕ заплатка на ядро

`TS Free VRAM` (`nodes/utils/ts_free_vram.py`, 12.9.0) снимает модели с карты
перед тяжёлым шагом через публичный API (`unload_model_and_clones` /
`unload_all_models`). Динамическая память остаётся включённой, `model_management`
не трогается. Тот же приём уже внутри `TS Latent Upscale`.

Патчить `model_management.py` было бы лечением не той болезни: механизм работает
как задуман, проблема в флагах одной ветки VAE.

⚠️ `--disable-dynamic-vram` — только диагностика, не решение: владелец
справедливо отказался отключать динамику, раз раньше с ней всё летало.

## Не проверено

Цепочка выведена из кода. Воспроизвести нельзя: нужен воркфлоу владельца, его
карта и перезапуск сервера. Подтверждение — строка в логе ноды о реально
освобождённых мегабайтах и скорость декода после неё.
