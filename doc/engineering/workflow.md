# Изменение и ревью

Совместимость сохранённого графа важнее косметики кода и архитектурной чистоты.

## Рабочий цикл

1. Прочитать относящийся к задаче код и [память подсистемы](../../project_memory/MEMORY.md).
2. Зафиксировать публичный контракт: node_id, имя класса и входов, порядок
   виджетов/выходов, типы, значения по умолчанию, category, extension IDs,
   сохранённые ключи node.properties и имена событий/маршрутов.
3. Найти потребителей общих модулей и выбрать минимальное изменение.
4. Реализовать только заказанное; не переписывать рабочую подсистему ради чистоты.
5. Выполнить [проверки по объёму изменения](../operations/testing.md), затем
   перечитать diff на скрытые побочные эффекты и потерю состояния.
6. Обновить документацию. Назвать проверенное и непроверенное, не выдавая
   статический разбор, skipped test или красивый скриншот за успешный inference.

Если исходное предположение не подтвердилось, пересмотреть его до дальнейшей правки.

## Контракт workflow

Без прямого запроса или согласованной миграции не менять node_id, Python class,
ключи NODE_CLASS_MAPPINGS, extension ID, имена и позиционный порядок входов и
выходов, типы, defaults, category, ключи сериализации и существующую семантику.
Снимок [контрактов](../../tests/contracts/node_contracts.json) хранит inputs и
outputs **списками с индексами**: alphabetic-сортировка виджетов не ловила
перестановки и позволяла молча прочитать старые widgets_values как другие настройки.
Новый необязательный вход обычно добавляется в конец; это не разрешение
самовольно менять остальные части контракта.

Отображаемое display_name отличается от node_id: изменение заголовка не требует
смены идентичности, но справка и локализация должны соответствовать итоговому имени.
При необходимом переименовании сохранить старый идентификатор/alias, описать
миграцию и проверить реальные старые графы. search_aliases помогают поиску,
но сами по себе не мигрируют сохранённый node_id.

## Границы рефакторинга

Допустимо при необходимости: private helper, действительно общий модуль,
уточнение типов, полезная validation, исправление утечки ресурсов. Большой файл
сам по себе не дефект. Нельзя ради рефакторинга менять поведение, добавлять
незапрошенные функции или дробить публичный класс на schema/execute/types.
Существующие исключения описаны в [правилах нод](node-api.md).

## Перед сообщением о готовности

- Идентификаторы и порядок widgets/outputs сохранены; добавленные поля сверены со схемой.
- Batch не потерян, входные тензоры не мутируются, dtype/device обработаны осознанно.
- Нет загрузки тяжёлой модели при импорте; optional-зависимость даёт понятную ошибку.
- Внешний процесс/файл имеет владельца, границы пути проверены, отмена и cleanup работают.
- Для UI проверены восстановление после смены workflow, cleanup слушателей и обе темы.
- Сообщение пользователю на русском, с результатом, проверками и существенными ограничениями.

Полномочия на commit/push, изменение версии и перезапуск не выводятся из этого
чек-листа. Их определяют [инструкции владельца](../../AGENTS.md).

## Приоритеты

Сохранённые workflow → совместимость и ожидаемое поведение → корректность →
проверяемость → поддерживаемость → производительность → архитектурная эстетика.
Новая функция появляется по запросу, а не как побочный результат уборки.
