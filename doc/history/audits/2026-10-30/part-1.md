## F-01 · [P2] Скрытые настройки TS-нод не подставляются в API prompt внутри subgraph

**Доказательность: PROVEN, статический разбор; применимость подтверждена исходниками установленного frontend 1.57.4.**

Основное место: [js/_dom_widget.js:75](../../../../js/_dom_widget.js#L75), `installPromptInjector`. Связанные места: [js/_dom_widget.js:495](../../../../js/_dom_widget.js#L495), [js/utils/ts-lora-loader.js:835](../../../../js/utils/ts-lora-loader.js#L835), [nodes/utils/ts_lora_loader.py:187](../../../../nodes/utils/ts_lora_loader.py#L187).

**Триггер.** Поместить TS LoRA Loader с непустым списком LoRA внутрь штатного subgraph и использовать его выход в выполняемом workflow.

**Цепочка.** LoRA UI вызывает hideWidget(loras_json). Helper сохраняет объект в _tsHiddenWidgets и удаляет его из node.widgets. Core собирает API inputs из оставшихся widgets и соединений. После этого wrapper пака проходит только `app.graph._nodes` и ищет результат по `String(node.id)`. Вложенные ноды не обходятся, составной execution ID не вычисляется.

В прочитанных sourcemap `src/utils/executionUtil.ts` и `src/lib/litegraph/src/subgraph/ExecutableNodeDTO.ts` core, наоборот, обходит inner nodes, формирует составные ID и берёт widgets из исходной ноды. Скрытого loras_json в этом массиве уже нет. Значения, сохранённые в workflow properties, сами по себе не становятся API inputs.

**Результат.** Требуемое поле loras_json отсутствует в запросе. В установленном backend `execution.py:914` пропуск required input приводит к `required_input_missing`. Наличие Python default="[]" не отменяет эту проверку. Сбой затрагивает и другие DOM-ноды, чьи скрытые обязательные параметры зависят от этого общего injector; точный список всех сочетаний ещё не установлен.

**Контрпроверка.** Копия в properties сохраняет workflow, но core API serializer не читает произвольные properties как inputs. Пропуск проводного значения wrapper-ом полезен, однако не обеспечивает обход subgraph. Нода на корневом уровне получает подстановку и не является данным сценарием.

**Рекомендация.** Обходить выполняемые ноды с теми же execution ID, что использует core, и сохранять приоритет реальных соединений. Исправлять общий helper, а не отдельно каждый UI.

**Регрессия.** Один и тот же LoRA workflow на корне и внутри subgraph: до постановки в очередь сравнить loras_json в конечном API prompt и проверить успешное применение выбранной LoRA. Проверить вложенный subgraph и повторное использование одной definition.

## F-02 · [P2] Поздний metadata-ответ Audio Loader заменяет состояние нового файла и может сбросить его обрезку

**Доказательность: PROVEN, статическая последовательность двух допустимых запросов.**

Места: [js/audio/loader/_audio_helpers.js:924](../../../../js/audio/loader/_audio_helpers.js#L924), `fetchMetadata`; [строка 757](../../../../js/audio/loader/_audio_helpers.js#L757), `applyMediaPayload`; [строка 734](../../../../js/audio/loader/_audio_helpers.js#L734), `syncWidgets`; [строка 1430](../../../../js/audio/loader/_audio_helpers.js#L1430), обработчик смены источника.

**Триггер.** Начать получение metadata файла A, выбрать B, дождаться B и задать диапазон; затем приходит более медленный ответ A.

**Цепочка.** Смена источника записывает B в state.sourcePath и запускает второй fetchMetadata. Ни идентификатора актуального запроса, ни сравнения пути перед применением ответа нет. Ответ A безусловно вызывает applyMediaPayload: заменяет duration/peaks/filename, адрес плеера и повторно вызывает syncWidgets. Например, если A имеет длину 1 секунду, а у B уже выбран старт 2 секунды, проверка cropStart >= duration сбрасывает начало в 0, конец — в -1. Эти значения пишутся в виджеты и properties.

**Результат.** Плеер и волна могут показывать A, хотя source_path остаётся B. Backend TS_AudioLoader применяет уже изменённые crop_start_seconds/crop_end_seconds к B. Пользователь может получить другой аудиофрагмент и изменить длительность lipsync не своим действием.

**Контрпроверка.** isLoading меняет статус, но не проверяется в обработчике смены источника и не защищает применение ответа. persist:false запрещает сохранение preview payload, но applyMediaPayload всё равно вызывает syncWidgets. restoringWorkflow относится к загрузке workflow, а не к актуальности сетевого ответа. В Video Loader аналогичный путь уже защищён metaToken; это не защита аудиозагрузчика.

**Рекомендация.** Принимать metadata, ошибку и завершающий статус только для текущего источника/поколения запроса; учитывать удаление ноды.

**Регрессия.** Управляемо задержать metadata A, вернуть B первым, задать диапазон 2–5 секунд и затем вернуть A либо его ошибку. Плеер, waveform и сохранённые crop-поля должны остаться от B. Проверить конечный AUDIO, а не только подпись файла.

## F-03 · [P2] TS Float Slider всё ещё меняет значение при восстановлении, если default не совпадает с сеткой step

**Доказательность: PROVEN, статическое противоречие нормализации и сохранения допустимого значения.**

Места: [js/utils/sliders/_slider_helpers.js:78](../../../../js/utils/sliders/_slider_helpers.js#L78), `tsSnapToStep`; [строка 251](../../../../js/utils/sliders/_slider_helpers.js#L251), precision/round; [строка 271](../../../../js/utils/sliders/_slider_helpers.js#L271), применение; [строка 333](../../../../js/utils/sliders/_slider_helpers.js#L333), восстановление.

**Триггер.** TS Float Slider: min=0, max=1, step=0.1, default=0.25; сохранённое значение 0.2. Эти настройки свойств допускаются существующим кодом, 0.2 удовлетворяет и Python-схеме.

**Цепочка.** После int-исправления float-ветка продолжает использовать default как anchor. Значение 0.2 привязывается к сетке 0.25 + n*0.1. Затем результат округляется до одного десятичного знака — по точности step. Получается 0.3 вместо 0.2. Восстановление через onConfigure вызывает этот путь с forceDefault=false, но это не предотвращает повторную привязку.

**Контрпроверка.** Sanitized config проверяет диапазон и знак step, но не согласует default с сеткой. Ограничение диапазона не помогает: оба значения внутри 0–1. Ранее добавленный int-фикс прямо сохраняет старую anchor-логику для float. Обычный default=0.5 при step=0.1 совпадает с сеткой и данный дефект не выявляет.

**Последствия.** Дробные параметры после переключения/перезагрузки могут отличаться от выбранных; касается настроек с несовпадающими default и step, а не каждого Float Slider.

**Рекомендация.** Согласовать сетку helper-а с фактической сеткой виджета и не изменять уже допустимое сохранённое значение. Отдельно определить поведение default вне сетки, не ломая легаси-диапазоны.

**Регрессия.** Сохранить 0.2 при указанном default=0.25; повторно восстановить workflow несколько раз в обоих интерфейсах. Должно остаться 0.2. Также проверить default=0.05, мелкие шаги и старые диапазоны.
